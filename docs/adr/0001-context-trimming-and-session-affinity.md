# ADR 0001：上下文裁剪策略 + 会话亲和性路由

- 状态：已采纳（ticket #9）
- 相关：#8（会话历史存进 Redis）、#7（worker 崩溃后的重新认领）

## 背景

#8 之后，每个 session 的历史存在 `session:<id>:history`（Redis list）里，每轮对话追加一条。这样有两个问题：

1. **历史无限增长**：聊得越久，list 越长。送进推理的上下文也越来越大，真实 LLM 会超出上下文窗口，成本和延迟也一起涨。
2. **同一 session 的请求会被任意 worker 处理**：所有 worker 抢同一条 Stream，谁先读到谁处理。同一个 session 几乎同时发来两个请求时，会被两个 worker 并行处理，读到的是同一份旧历史，后一个请求"看不到"前一个。

## 决策一：上下文裁剪用"最近 N 轮"滑动窗口

- 每个 session 最多保留最近 `maxHistoryTurns` 轮（默认 20，最小 1），超出的最早几轮**直接删除**。
- **写时裁剪**：`RPUSH` 和 `LTRIM -N -1` 放在同一个 `MULTI` 里执行。Redis 里的存储本身有上限，而不是只在读的时候截断。
- **读时也只取最后 N 条**（`LRANGE -N -1`）：即使配置调小过、底下残留了更长的 list，送进推理的上下文也不会超限。

### 为什么选按轮数，而不是按 token 数或做摘要

| 方案 | 优点 | 缺点 |
|---|---|---|
| **最近 N 轮（采用）** | 实现简单，一条 `LTRIM` 搞定；行为可预测，容易测试 | 每轮长短不一，N 轮的实际 token 数不固定 |
| 按 token 预算裁剪 | 能精确贴合模型的上下文窗口 | 需要分词器；mock 推理阶段没有真实 token |
| 摘要旧历史（用 LLM 压缩） | 保留更久远的信息 | 要额外调用一次模型，有成本、有延迟，还可能失真 |

现阶段推理是 mock，没有真实 token 数可算，先用轮数。接入真实 LLM 后，可以在读取时再加一层 token 预算：从最新一轮往前累加，超出预算就停。存储层的 N 轮上限继续保留，作为兜底。

## 决策二：按 worker 分片的 Stream + rendezvous 哈希路由

只有一条共享 Stream 时，网关决定不了任务交给谁。所以改成**每个 worker 一条自己的 Stream**：`<streamKey>:<worker 序号>`。每个分片仍然有 Consumer Group，ack / pending / 重新认领的机制不变。

网关派发时决定分片：

- **有 sessionId**：用 rendezvous（最高随机权重）哈希。对每个**存活**的 worker 算 `sha1(sessionId#worker)`，取分数最高的。同一个 session 永远落到同一个 worker。某个 worker 下线时，只有原本属于它的 session 会换 worker，其它 session 不动。普通的 `hash % N` 在 N 变化时几乎所有 session 都会换。
- **没有 sessionId**：不需要亲和性，交给当前负载（已派发未完成数）最低的 worker。

worker 的处理顺序：

1. 扫**所有**分片的 pending 列表，认领超时（stale）的任务（#7 的崩溃恢复；挂掉的正是别的分片的主人）。
2. 阻塞读自己的分片。
3. 自己的分片空闲时，帮已下线的 worker 清空其分片里**还没被读走**的任务。这些任务不在任何人的 pending 列表里，第 1 步找不到它们。

### 读历史放到 worker 里

读历史和组装上下文改在 worker 开始推理前做，不再在网关派发时做。同一个 session 的请求在同一个 worker 上**依次**执行，后一个请求开始推理时，前一个请求的这一轮已经写进历史了。亲和性因此有了可观测的收益：同一 session 的并发请求不会互相"看不到"。

## 代价与已知限制

- **负载可能不均**：一个特别活跃的 session 会让它的 worker 排队，即使别的 worker 闲着。常见的改进是"有上限的亲和性"（bounded-load consistent hashing）：首选 worker 的负载超过平均值一定比例时，溢出到下一个候选。目前没做。
- **崩溃后不再保证串行**：worker 挂掉后，它的 session 会转到别的 worker。正在被重新认领的旧任务和发到新 worker 的新任务，可能短暂并行。
- **存活名单是进程内标记**：`killWorker` 同时充当健康检查。真实的多进程部署里，这份名单应该来自心跳 / 注册中心，存在判定延迟。
- **亲和性只是"倾向"**：会话历史始终在 Redis 里，不在 worker 内存里，所以换了 worker 也不会丢上下文。亲和性提供的是顺序性，以及将来做本地缓存（如 KV cache 复用）的可能，不是正确性的前提。
